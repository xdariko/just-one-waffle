## Решения (кратко, с причинами)

- **Временные скрипты проверки** (`TmpVerify`, `TmpSmoke`, `TmpContentBootstrap`) удалены после прогона; тестовой инфраструктуры в проекте не добавлялось.
- **ScriptableObject для импортированных данных** — так уже хранятся `WaffleRecipe` и `DecorIngredient`; ссылки из сцен и ассетов идут по GUID, поэтому обновление существующего ассета на месте не рвёт их; Unity-настройки редактируются в инспекторе.
- **Разделение импорт / Unity**: всё, что пришло из JSON, лежит в блоке `source` ассета (импортёр пишет только туда). Числа рецепта (яйца, граммы, порции, соусы, добавки) — производные от `source`, их пересчитывает импорт; допуски зон, выпечка, тесто, реплики, визуал, `kind` ингредиента — только Unity, импорт их не трогает.
- **Ключи**: тег — `name`, ингредиент — `id`, рецепт — `name` (других идентификаторов в экспорте нет). Переименование рецепта на сайте = новый рецепт.
- **Исчезнувшие записи** не удаляются: помечаются `missingInLastImport`, попадают в отчёт; заказы с такими рецептами исключаются из случайного выбора и подсвечиваются проверкой контента.
- **Запись с битой ссылкой** не создаётся и не обновляется (остаётся прошлая версия), остальные импортируются; ошибка — в отчёте.
- **Свой парсер JSON** (~250 строк), а не пакет: в проекте нет Newtonsoft, `JsonUtility` не читает разнородные компоненты, а пример экспорта не является строгим JSON. Парсер понимает оба варианта.
- **Количество компонента по виду ингредиента**: яйца — штуки, мука — г, молоко — мл, сахар — г, соль — порции, соус — % покрытия, добавка — штуки. Вид (`kind`) задаётся в Unity у `CraftIngredient`.
- **Точное совпадение рецепта** (`OrderTemplate.match = ExactRecipe`): состав должен соответствовать рецепту (нужные ингредиенты есть, лишних базовых нет, нужные соусы и добавки есть), свойства-теги рецепта подтверждены результатом. Количества влияют только на качество.
- **Заказ по требованиям** (`match = Requirements`): проверяются только требования-теги (`MustHave`/`MustNotHave`); подходит любой рецепт из списка (пустой список — любой рецепт базы). Качество считается по самому близкому совместимому рецепту, поэтому recipeId не влияет на принятие. Нормы на шкалах — по `guideRecipe` заказа или по самому подходящему рецепту.
- **Свойства результата**: теги всех реально добавленных ингредиентов + теги выпечки (`WaffleRules`: «зажаристая» → `crispy`, и т. д.).
- **Реакция**: есть нарушенное требование → недоволен, при любом качестве; иначе качество ≥ 80% → доволен, ≥ 50% → нейтрален, ниже → недоволен (пороги в `WaffleRules`).

### Правила дня

- Время идёт, пока день открыт: в диалоге, на кухне и во время реакции. Не идёт на экране начала дня и итогов.
- Время вышло — новые обычные клиенты не приходят. Клиент, уже стоящий у стойки или ждущий вафлю, обслуживается до конца.
- Сюжетный визит «начало дня» — первые клиенты дня. «Случайный момент» — в момент из окна `[min..max]` доли дня встаёт в приоритетную очередь; если игрок занят, клиент приходит сразу после текущего. «Конец дня» — после истечения времени и текущего заказа, перед итогами. Если время кончилось раньше случайного момента, визит всё равно проходит перед итогами.
- Несколько сюжетных визитов на одной позиции — по `priority` (больше — раньше), затем по `id`.
- `once`: визит засчитывается в момент появления клиента и больше не повторяется даже при перезагрузке сцены. Системы сохранений в проекте нет, прогресс хранится в `DayRunner` в пределах текущего запуска.
